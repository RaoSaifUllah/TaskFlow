# ADR-009: Persist accepted authenticator windows
Status: accepted, 2026-10-04

Identity remains the account lifecycle and authenticator-secret provider. Reviewing
its v10.0.12 AuthenticatorTokenProvider source showed verification checks valid
codes but does not persist accepted windows. TaskFlow requires TOTP single use.

Use pinned Otp.NET 1.4.1 (previously an interoperability test dependency) to obtain
the matched 30-second window after Identity validation. Narrow acceptance to one
past/current/one future window. Under a per-user PostgreSQL row lock, persist the
unique (UserId, AuthenticatorGeneration, Step) before committing enrollment, login
or step-up. No OTP value or authenticator secret is persisted in this record.
Enrollment-key reset rotates a random generation ID; stamp/session changes alone
do not reset replay history. Repeated codes fail safely, including cross-endpoint
and concurrent replay. Users must wait for a new code after enrollment/login.

Runtime roles can SELECT/INSERT use records but cannot UPDATE/DELETE them. Retention
of expired generations/windows belongs to a privileged operational cleanup policy
in Phase 7. This is a targeted replay guard, not a security certification claim.
